# 文章レイヤー

文章レイヤーは、完成本文を変更せず、本文の特定箇所に結び付く作業情報や補足をGitHub Pages上で表示する仕組みです。`chapters/*.md` は読者向けの完成本文、`docs/document-design/` は文書全体の目的と設計意図、`_data/layers/` は文書メタ情報への導線と局所的な補助情報を担当します。文章レイヤーは設計メモを置き換えません。

## 構成

- `_data/layer_types.json`: 利用できる種別、表示名、light・dark用の表示色の定義
- `_data/layers/<章名>.json`: 対象章とエントリ
- `scripts/validate_layers.py`: データとアンカーの検証
- `scripts/embed_layers.py`: Jekyllの生成済みHTMLへページ分のデータを埋め込む処理
- `scripts/test_embed_layers.py`: 全対象章の生成済みHTMLへアセットと章別データを一度だけ埋め込めることの検証
- `assets/js/layers.js`、`assets/css/layers.css`: ブラウザ上の表示

Primerのlayoutは複製しません。PagesのJekyllビルド後、デプロイ対象のHTMLだけへ既存の本文を変更せずにCSS、JavaScript、そのページに必要なJSONを追加します。JavaScriptが無効な場合は、従来どおり本文だけが表示されます。

## `view.html` 対応の進め方

`view.html` という名前の独立ページやlayoutは、現在のリポジトリとGit履歴にはありません。現行実装では、閲覧用ページを新設する代わりに、Jekyllが生成した各章のHTMLへ文章レイヤーを埋め込みます。したがって、名前だけを根拠に `view.html` を追加せず、まず現行方式が必要な閲覧機能を満たすか確認します。

対応は、変更と判定を混ぜないよう次の単位に分けます。

1. **役割の確認（完了）**: `view.html` の既存実装と履歴を調べ、現行の生成後埋め込み方式との関係を記録する。
2. **現行方式の最小確認（自動確認まで完了）**: 最小の生成済みHTMLを使い、レイヤーを持つ全章へCSS、JavaScript、章別データを埋め込めることをCIで確認する。Jekyllで生成したページ上の本文、Layerパネル、挿入位置、表示切り替えは目視確認として残す。
3. **不足の判定**: 専用URL、章をまたぐ閲覧、編集用表示など、現行方式で満たせない役割があるかを確認する。
4. **必要な場合だけ実装**: 不足が確認された場合に限り、`view.html` または同等の入口を最小構成で追加する。既存ページと機能が重複するだけなら追加しない。
5. **表示条件の確認**: モバイル幅、light/dark、JavaScript無効時を順に確認し、結果を記録する。

各段階は一つずつコミットします。第2段階の確認前に専用ページを作らないことで、Primerのlayout複製と二重の閲覧経路を避けます。進捗と終了条件は [`progress.md` の #23](progress.md#23-文章レイヤーの試験運用を完了する)を正本とします。

## レイヤーファイルの書き方

```json
{
  "target": "chapters/02-scalability.md",
  "documentDesign": "docs/document-design/02-scalability.md",
  "entries": [
    {
      "type": "research",
      "anchor": "本文中で一度だけ現れる文字列",
      "content": "表示する補助情報",
      "prefix": "必要な場合だけ指定する直前の文字列",
      "suffix": "必要な場合だけ指定する直後の文字列",
      "position": "after"
    }
  ]
}
```

文書単位では `target`、`documentDesign`、`entries` が必須です。`documentDesign` は、その章の目的、中心メッセージ、責務、扱わないこと、見送った案を保持する設計メモを指定します。PagesのLayerパネルは「章の目的・設計判断」というリンクだけを表示し、設計メモの内容を複製しません。

各エントリでは `type`、`anchor`、`content` が必須です。`prefix` と `suffix` は短いアンカーを文脈で一意にする場合に使います。`position` は `after`（既定）または `before` を指定できます。Markdownの装飾記号を除いた文字列でも照合できるため、ブラウザでは対応する段落などの前後へ補助情報を挿入します。

種別を増やす場合は `_data/layer_types.json` に定義を追加します。表示コードと検証コードへ種別名を追加する必要はありません。

各種別には、表示名の `label`、light表示用の `color`、dark表示用の `darkColor` を指定します。色は `#` から始まる6桁の16進表記にします。色だけで種別を伝えず、パネルと補助情報には常に表示名を併記します。

## 執筆と表示

本文にレイヤー専用のIDやコメントは書きません。補助情報を追加したら、`python3 scripts/validate_layers.py` で対象ファイル、種別、アンカーの一意性を確認します。

レイヤーがあるPagesでは、右上の「Layer」パネルから種別ごとに表示を切り替えられます。初期状態は本文のみです。「本文」をオフにすると補助情報を確認しやすい表示になりますが、本文ノード自体は書き換えません。同じパネルから文書設計メモを開けるため、文書全体のメタ情報と本文中の局所レイヤーを一つの入口から参照できます。

## 追加とレビューの手順

レイヤーは次の順で一文書ずつ追加します。

1. 文書全体の目的や見送った案なら、先に `docs/document-design/` の設計メモへ記録し、`documentDesign` から参照する。
2. 本文の一箇所に結び付く情報だけを、対象章と同名の `_data/layers/*.json` へ追加する。
3. 本文にレイヤー用の文言やアンカーIDを足さず、既にある特徴的な一文を `anchor` に選ぶ。
4. `python3 scripts/validate_layers.py` と `python3 scripts/test_embed_layers.py` を実行する。
5. レビューでは、情報の置き場所、アンカーの意味上の位置、本文だけで読めること、light・darkの判読性を確認する。

本文を変更したレビューでは、通常の文章確認に加えて対象章のレイヤー検証を必須とします。アンカーが偶然別の一箇所へ一致する場合は自動検出できないため、一致数だけでなく意味上の位置も確認します。設計メモとレイヤーに同じ判断を置く場合、設計メモを正本と明記し、レイヤーは該当箇所から判断へ到達するための短い案内にとどめます。

## 試験適用の範囲

第2章では、発想、調査、別案を各1件保持します。いずれも設計メモの判断を本文の該当箇所から参照する案内であり、本文や設計メモの代替にはしません。

準備章では、三つの分離を区別する発想と、問い合わせ手順を先に説明しない別案の2件を適用します。これにより、第2章だけに依存せず、章ごとに異なる件数を生成後HTMLへ埋め込めることを確認します。試験中は他章へ広げず、この2文書で運用を判定します。

## 制約

アンカーは本文の文字列に依存するため、本文の改稿時に追随が必要です。CIは不一致を検出しますが、意味的に別の箇所へ偶然一意に一致した場合までは判定できません。長すぎない特徴的な文を選び、必要なら `prefix` と `suffix` を併用します。

基盤の実装後に残る表示確認と試験運用は、[`progress.md` の #23](progress.md#23-文章レイヤーの試験運用を完了する)で追跡します。
