# 文書設計メモ

本文だけでは失われやすい「なぜこの構成にしたか」を、本文とは別に残すための記録です。完成した文章の要約ではなく、執筆時の判断と、その判断を見直す条件を扱います。

## 本文・進行状況との役割分担

- 本文には、読者が理解するために必要な説明と出典を置きます。
- このディレクトリには、対象読者、文書の責務、扱わない範囲、採用した構成、見送った案、未決事項を置きます。
- [`progress.md`](../progress.md) には、作業の順序、依存関係、完了条件を置きます。
- 複数の文書に影響する方針は、[`concept.md`](../concept.md)、[`outline.md`](../outline.md)、[`style-guide.md`](../style-guide.md) など、該当する共通文書へ反映します。設計メモだけを正本にはしません。

設計メモは対象文書と相互にリンクします。本文を変更するたびに経緯を追記するのではなく、文書の責務、論旨、構成、または意図的な非採用事項が変わるときに更新します。古い判断は消さず、変更日と変更理由を添えて残します。

## レビューでの使い方

1. 対象文書から設計メモを開きます。
2. 本文の正確性と読みやすさに加え、「目的」を達成し、「中心メッセージ」が一貫し、「読者に渡すもの」と「この文書の責務」を満たしているかを確認します。
3. 「扱わないこと」を持ち込んでいないか、理由を変えずに「見送った案」を復活させていないかを確認します。
4. レビュー結果に、設計メモを確認したことと、不一致の有無を書きます。
5. 意図的に方針を変える場合は、本文と設計メモのどちらを正しい状態にするかを明示し、両方の更新を提案します。

設計メモは本文を固定するためのものではありません。過去の判断を知らずに偶然変更することと、前提の変化を確認して判断を更新することを区別するために使います。

## 既存文書からの復元

設計メモが残っていない既存文書は、現在の本文から設計意図を復元します。ただし、本文から読み取れる構造と、当時の筆者が実際に考えたことは同じとは限りません。次の順で根拠を確認します。

1. 対象文書に明記された目的、範囲、注記
2. `concept.md`、`outline.md`、`mechanism-map.md`、`progress.md` にある役割分担や判断記録
3. コミットメッセージと対象箇所のGit履歴
4. 上記から直接確認できず、現在の文章から推定した内容

復元したメモには `記録種別: 既存資料からの復元` と復元元を記載します。確認できた判断と推定を分け、根拠のない「見送った案」は作りません。不明な点は `TODO: 要検証` とします。復元と本文の改稿は同時に行わず、一文書ずつ小さな差分で確認します。

## 記録する項目

新しい設計メモは、次の項目から必要なものを使います。未決事項は結論のように書かず、判断者と判断条件が分かる形にします。

- **目的**は、その文書をなぜ作るのか、読者のどの問題を解くのかを書きます。
- **中心メッセージ**は、読み終えた読者に一つだけ残す主張を書きます。
- **読者に渡すもの**は、読後に読者が説明または判断できるようになることを書きます。

目的、中心メッセージ、読後の変化を分けることで、扱う項目を増やすこと自体が目的になるのを避けます。

```markdown
# 「文書名」の設計メモ

- 対象文書:
- 状態:
- 記録種別: 執筆時の記録 / 既存資料からの復元
- 復元元: （復元の場合）
- 最終更新:

## 目的
## 中心メッセージ
## 読者に渡すもの
## この文書の責務
## 扱わないこと
## 採用した構成と理由
## 見送った案
## 未決事項と見直す条件
## 判断履歴
```

「見送った案」には、単に不採用とだけ書かず、見送った理由と、どの条件が変われば再検討するかを書きます。候補に挙がらなかった案を網羅する必要はありません。
