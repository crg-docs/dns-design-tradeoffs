# 準備章「なぜ名前解決が必要なのか」の設計メモ

- 復元元: 対象文書、[`outline.md`](../outline.md)、[`mechanism-map.md`](../mechanism-map.md)、[`progress.md`](../progress.md)、対象文書のGit履歴
- 最終更新: 2026-08-22

## 目的

第2章以降でDNSの設計を非機能要件から評価する前に、名前解決が必要になる理由と、DNSに固有ではない名前解決、DNSが分割した管理責任を区別できるようにします。あわせて、後続章の設計判断を読むために必要な最小限の用語を渡します。

## 中心メッセージ

名前と通信に必要な情報を分けること、その二つを利用時に結び付けること、対応情報の管理責任を分けることは、それぞれ異なる問題です。DNSは名前解決そのものを発明したのではなく、規模と更新主体が増えても対応情報を管理し、参照できるようにする方法を変えました。

## 読者に渡すもの

- 名前、通信に必要な情報、名前解決、管理責任の分割を別の概念として説明するための語彙。
- 名前空間、ドメイン、ゾーン、委譲、権威情報という語が、後続章で何を区別するために使われるかという見取り図。
- DNSの初期目的と、Web、負荷分散、障害時の切り替えといった後から広がった用途を区別する視点。

## この文書の責務

- 人やアプリケーションが保持する名前と、その時点で通信に必要な情報を分ける理由を説明します。
- DNS以前にも名前解決と対応表が存在したことを示し、名前解決とDNSを同一視しないようにします。
- 対応情報の管理と参照を一つの一覧へ集中させないことが、初期DNSの中心的な課題だったと示します。
- 第2章を読む前提として、名前空間、ドメイン、ゾーン、委譲、権威情報の関係を短く導入します。

## 扱わないこと

- 委譲が中央の作業量をどう減らし、どの境界問題を増やすかという評価は第2章へ残します。
- 再帰・反復問い合わせ、キャッシュ、Time to Live（TTL）の機能説明は第3章へ残します。
- レコード型、DNSメッセージ、設定方法を網羅する用語集にはしません。
- 負荷分散、障害時の切り替え、変更反映を初期DNSの目的として遡及させません。

## 採用した構成と理由

### 三つの分離を区別する

値の役割を分けること、分けた値を利用時に結び付けること、対応情報の管理を分担することを順に示します。「DNSはIPアドレスを覚えなくて済むようにする」という説明だけでは、DNSが必要になった管理上の問題まで説明できないためです。

### 第2章の前提語彙を短く導入する

第2章が拡張性を求める利用者と管理者の課題を主題にするには、用語の定義で議論を中断しない構成が必要です。そのため、名前空間、ドメイン、ゾーン、委譲、権威情報の関係はこの章で導入します。ただし、辞書のように列挙せず、名前の構造と管理責任の境界が同じとは限らないことを説明する一つの関係として扱います。

## 見送った案

### DNSの問い合わせ手順まで先に説明する

準備章がDNSの概説になり、本書が非機能要件を主軸にするまでの距離が長くなるため扱いません。第2章を読むために不要な機能説明は、各仕組みを評価する章で導入します。

### 第2章の効果と代償を移す

用語だけでなく設計評価まで準備章へ移すと、第2章の中心メッセージが重複するため扱いません。準備章は語を区別できる状態まで、第2章はその語を使って設計を評価できる状態までを責務とします。

## 未決事項と見直す条件

- 用語の導入に使う図と本文の分量は未決定です。第2章から用語説明を除いた後も、準備章だけで関係を説明できる最小限の形を選びます。
- 「権威情報」と「権威サーバー」の両方を定義するかは、改稿後の第2章で必要になる語を確認して決めます。
