# 執筆スタイルガイド

## 文体と構成

- 平易で、過度にくだけない「です・ます」調を基本とする。
- 用語を初出時に定義し、英語の略語は初出時に正式名称を展開する。
- 一文に複数の論点を詰め込まず、過度に長くしない。
- 機能の説明より先に「なぜ必要になったか」を示す。
- 単なる機能一覧にせず、設計の利点と代償を対にして書く。
- 現代の資源、脅威、運用慣行を前提として、過去の設計を安易に批判しない。
- 「セキュア」「高可用」「高速」などは、それが何の脅威、障害、指標を指すか具体化する。

## 用語と時制

- 現行用語は RFC 9499 を第一の基準とする。
- 歴史資料固有の語は、当時の語であることを明示する。
- `ドメイン名`、`名前空間`、`ゾーン`を同義語として扱わない。
- `権威サーバー`、`再帰リゾルバ`、`スタブリゾルバ`の役割を区別する。
- 仕様の記述には「規定する」、観測や評価には「示す」「考えられる」を使い分ける。

## 出典、引用、注記

- 歴史と仕様は一次資料を優先し、出典を該当段落の直後に置く。
- Markdownリンクは資料名と番号が分かる表記にする。例: `[RFC 1034: Domain Names—Concepts and Facilities](https://www.rfc-editor.org/rfc/rfc1034.html)`。
- 引用は必要最小限とし、引用符またはブロック引用で要約と区別する。ページまたは節を示せる場合は示す。
- RFCの更新・廃止関係と、規範語の強さを保つ。個別規定から一般原則を導く場合は、本書の解釈だと明記する。
- 確認できない歴史的事実には `TODO: 要出典`、意味や妥当性の再確認には `TODO: 要検証` を付ける。
- 出典の役割は `references/sources.md` に記録し、番号だけを列挙しない。

## 図と実測

本書はWebで読まれる。文字だけで押し通さず、図と実物の観測を使う。

- 経路、階層、時間の前後関係、データの流れは図示を検討する。特に委譲関係、問い合わせ経路、キャッシュの期限、複製の伝播は文章より図が向く。
- 図は本文の言い換えにしない。並行、分岐、時間差のように、散文では書きにくい関係を図に担わせる。
- 仕組みを説明したら、可能な範囲で実物を示す。実際のドメインへの問い合わせ結果、レコードの内容、応答の差異など。
- 観測を載せるときは、コマンド、実行日時、観測地点、対象ドメインを併記し、再現条件を明示する。
- 観測結果は一次資料ではない。仕様の裏付けにはRFCを使い、観測は「その時点、その地点でそう見えた」記録として区別する。
- TTLの残り時間、Anycastの応答、権威サーバーの一覧は観測時点と地点で変わる。値を本文へ引く場合は、変わり得ることを明記する。
- 第三者のドメインを観測対象にする場合は、通常の名前解決の範囲を超える負荷をかけない。

### 図の入れ方

- 既定は mermaid のコードフェンス（` ```mermaid `）を使う。階層構造、委譲、問い合わせ経路に向く。ゾーン境界は `subgraph` で表す。
- mermaid の図を置いたページは、末尾に `{% raw %}{% include mermaid.html %}{% endraw %}` を1行書く。これがないと図はコードブロックのまま表示される。
- 時間軸を持つ図（TTLの満了、変更反映の時間差、複製の伝播、年表）は mermaid では書きにくいため、手書きのインラインSVGを使う。`viewBox` と `width="100%"` を指定し、`role="img"` と `aria-label` で内容を説明する。
- 項目数の多い時間軸図は**縦に並べる**。Webページでは幅が希少で高さは自由に使えるため、横に並べると図の自然幅が本文幅を超え、`max-width` で縮小されて文字が読めなくなる。mermaid の `timeline` はこの理由で使わない。
- 図には必ず本文からの参照を置き、図だけで理解させようとしない。逆に、図がなくても筋が通る文章にする。

## 章末の構成

すべての章の末尾に、次の3つをこの順で置く。

```markdown
## この章の言い換え

| 前 | 後 |
| --- | --- |
| 「DNSが遅い」 | 「委譲の段数が多く、初回の問い合わせがキャッシュに乗っていない」 |

## 参照資料

- [RFC 1034: Domain Names—Concepts and Facilities](https://www.rfc-editor.org/rfc/rfc1034.html) 2.1節

---

[← 前の章](.md)｜[目次](../)｜[次の章 →](.md)
```

- **言い換え**は、その章を読む前に使っていた曖昧な言い方を左に、読んだ後に使える具体的な言い方を右に置く。副題「「DNS」と言わずに説明する」の達成度を測る場所である。左に「DNS」を含み、右に含まないのが基本形。
- 1章あたり2〜4組にとどめる。多いと要約表になり、読者が本文を読まなくなる。
- **参照資料**は本文で使った出典を列挙し、節を示せる場合は示す。`references/sources.md` に未登録の資料を本文へ引かない。
- **ナビゲーション**は前後の章と目次への導線を置く。最初と最後の章は該当する項目を省く。

## 章の基本単位

1. 要件の定義
2. 具体的に何が問題になるか
3. DNSで採用された設計
4. 設計が必要になった歴史的背景
5. 得られる効果
6. 新しく生じる制約
7. 他の非機能要件との衝突
8. 運用上の注意
9. 現代のシステム設計への応用（類似点と適用限界を含む）
10. 参照資料

章の主語は非機能要件とする。歴史を独立した物語として先に置かず、設計理由を説明するために必要な範囲で配置する。
