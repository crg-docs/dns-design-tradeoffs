# 仕組みの分担表

DNSの仕組みは複数の章に登場する。同じ機能説明を繰り返さず、章ごとに評価の軸を変えるための割り当て表である。`outline.md` が示す方針の実装であり、章本文を書く前に参照する。

## 使い方

1. 詳細な機能説明は準備章の独立した項へ置き、本編から直接リンクする。
2. 本編はDNSの要求から必要な非機能要件と解決を追う。下表は機能を全て説明する義務ではなく、同じ仕組みを見る際の評価の違いを示す。
3. 観測手順と生データへの導線は準備章へ、結果が何を示すかは本編にも残す。
4. 詳細項目の入口は[準備章の索引](../chapters/01-name-resolution.md#必要な説明を引く)とする。

## ゾーン転送

詳細: [準備章：ゾーン転送と変更通知](../chapters/01-name-resolution.md#ゾーン転送と変更通知)

全転送（AXFR）、差分転送（IXFR）、変更通知（NOTIFY）を区別する。1987年のRFC 1034の4.3.5節は定期確認と全量転送を定めている。1996年のIXFRとNOTIFYは、その転送量と反映までの待ち時間を減らす追加である。この経緯は第1章の年表が扱う。

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第4章 | 可用性 | 複製の台数、複製が揃うまでの時間 |
| 第5章 | 整合性 | Serialの一致、複製間の差異が解消するまでの時間 |
| 第6章 | セキュリティ | 転送の認証と、転送先の制限 |
| 第8章 | 運用性 | 複製の同期を観測できているか |

## 機能要件を曲げた事例

第10章の総括で回収する、非機能要件が機能の形を変えた例です。以下は本書による設計上の整理であり、元来の要件が一つだったという歴史的な主張ではありません。

| 仕組み | 何を曲げたか | 主な章 |
| --- | --- | --- |
| キャッシュとTTL | 問い合わせごとに最新の答えを返すことをやめ、一定期間は過去の答えを返す | 第3章、第5章 |
| Serve Stale | 更新できないときに期限切れデータを使い、最新性の保証を弱めて応答を継続する | 第4章 |
| Negative Caching | 現在の不在ではなく、過去の不在を答える | 第3章、第5章 |
| DNSSECの検証 | 届いた情報でも、必要な検証が成立しなければ利用しない | 第6章 |
| 情報の最小化 | すべての上流に完全な問い合わせを渡すことをやめ、必要な範囲に絞る | 第7章 |
| 未知のRR型の取り扱い | 意味を理解することと、その情報を保存・転送することを分ける | 第9章 |

各行の評価を第10章の総括へ接続しています。新たな事例を加えるときも、改善する対象と引き受ける代償を対にします。
