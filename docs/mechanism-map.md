# 仕組みの分担表

DNSの仕組みは複数の章に登場する。同じ機能説明を繰り返さず、章ごとに評価の軸を変えるための割り当て表である。`outline.md` が示す方針の実装であり、章本文を書く前に参照する。

## 使い方

1. 仕組みごとに**機能説明を担当する章**を1つ決める。その章だけが「どう動くか」を説明する。
2. 他の章は機能説明を繰り返さず、担当章を参照した上で、**その章の要件から評価する**。
3. 各章が使う**指標**を分ける。指標が同じなら、その仕組みをその章で扱う理由がない。
4. 表にない仕組みを本文で複数章にまたがって使う場合は、この表へ追加してから書く。

## キャッシュ

機能説明の担当: **第3章**（応答を再利用する仕組みとして導入する）

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第3章 | 性能 | 問い合わせ数、キャッシュヒット率、権威サーバー負荷、名前解決の遅延 |
| 第4章 | 可用性 | 上流障害中に応答できた割合、影響を受けた利用者の範囲 |
| 第5章 | 整合性、変更反映 | 変更が全観測地点へ反映されるまでの時間 |
| 第6章 | セキュリティ | 偽造応答を受け入れる確率、汚染が残存する時間 |

## TTL

機能説明の担当: **第3章**（再利用期間の制御として導入する）

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第3章 | 性能 | 再利用期間の長さとキャッシュヒット率の関係 |
| 第5章 | 変更反映 | 変更反映までの下限時間、切り戻しに要する時間 |
| 第6章 | セキュリティ | 汚染されたデータが残存する時間 |
| 第8章 | 運用性 | 変更前のTTL短縮が計画に含まれているか |

## Serve Stale

機能説明の担当: **第4章**（上流へ到達できないときの応答継続として導入する）

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第3章 | 性能（最悪時） | 上流が遅いときの応答時間の上限 |
| 第4章 | 可用性、障害耐性 | 障害中に応答を継続できた時間 |
| 第5章 | 最新性 | 期限切れデータを返した期間 |

第3章では平均性能と最悪時性能を調整する発展例として短く触れ、可用性としての評価は第4章で行う。

## Negative Caching

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第3章 | 性能 | 不在応答による問い合わせ削減 |
| 第5章 | 変更反映 | レコード追加後に不在情報が残る時間 |

## 委譲とゾーン

## ゾーン転送

機能説明の担当: **第4章**（複製を配布する仕組みとして導入する）

全転送（AXFR）、差分転送（IXFR）、変更通知（NOTIFY）を区別する。IXFRとNOTIFYは1996年の追加であり、1987年の仕様は複製の存在を定めたが、いつ何を送るかは規定していなかった。この経緯は第1章の年表が扱う。

| 章 | 評価する要件 | 指標 |
| --- | --- | --- |
| 第4章 | 可用性 | 複製の台数、複製が揃うまでの時間 |
| 第5章 | 整合性 | Serialの一致、複製間の差異が解消するまでの時間 |
| 第6章 | セキュリティ | 転送の認証と、転送先の制限 |
| 第8章 | 運用性 | 複製の同期を観測できているか |

## 機能要件を曲げた事例

第10章の総括で回収する。非機能要件が機能そのものの形を変えた例を、各章の執筆時にここへ追記する。

| 仕組み | 何を曲げたか | 主な章 |
| --- | --- | --- |
| キャッシュとTTL | 問い合わせごとに最新の答えを返すことをやめ、一定期間は過去の答えを返す | 第3章、第5章 |
| Serve Stale | 期限切れと分かっているデータを返す。正しい答えを返すという機能を明示的に降りている | 第4章 |
| Negative Caching | 現在の不在ではなく、過去の不在を答える | 第3章、第5章 |
| （執筆時に追記） | | |

この表は、非機能要件が機能要件の形すら決めるという主張の証拠になる。空欄のまま第10章を書かない。
