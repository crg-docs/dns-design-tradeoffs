# 第2章 拡張性――集中管理を分割する

> この章は本文化の途中である。第1節は本文、それ以降は構成案である。
>
> 年表と出来事の順序は第1章（見取り図）が担当する。この章では年表を再語りせず、集中管理がなぜ壊れるのか、委譲が責任をどう分割するのかという構造の分析に集中する。
>
> **この章は章構成の試作でもある。** 結論を冒頭へ置く形を試し、全体の本文化と著者の判定が済んだ後に、第3章以降へ適用するかを決める。

## 1. この章の結論

DNSは、名前の一意性を担保する責任と、データを更新する権限を、名前空間の部分木ごとに分割しました。中央がすべての登録を処理する代わりに、親側の管理主体は子側の管理主体へ一部を委ね、子側へ問い合わせを進めるための情報を保持します。これにより、個々の組織のデータ変更まで中央で処理せずに済みます。その代わり、委譲情報とゾーン境界を正しく保ち、委譲先の権威サーバーへ到達できるようにする必要が生じます。問題の切り分けも、単一の表を調べる形から、複数の管理主体と参照関係をたどる形へ変わります。

ただし、ここから「集中管理は悪く、分散管理は正しい」とは結論できません。この設計へ至るまでには、次の三段階がありました。

| 段 | 状態 | 何が問題だったか |
| --- | --- | --- |
| 第一段（1973年まで） | 不統一な分散。各サイトが自前のホスト表を手で維持 | どれも不完全で、互いに食い違っていた |
| 第二段（1974〜1980年代前半） | 集中。中央が一つの表を維持し、各ホストが取得 | 規模と更新主体の増加で、中央の調整が詰まった |
| 第三段（1983年以降） | 委譲による分散。階層化して責任を分ける | 依存関係と切り分けの複雑さが増えた |

最初の集中管理は、不完全な表を各サイトが別々に維持する状態への対処でした。その後、規模と更新主体が増えたことで、今度は中央で一つの表を管理する方法が制約になりました。同じ「名前の一意性を保ち、更新を利用者へ届ける」という問題に対して、条件の変化に応じて逆向きの設計が選ばれたのです。設計を評価するときは、集中か分散かという分類だけでなく、その選択が成立した規模、更新頻度、管理主体の数を確かめる必要があります。

## 2. 要件の定義と評価観点

ここでの拡張性は、ホストやデータの件数だけでなく、更新頻度、更新主体、問い合わせ元、管理組織が増えても、中央の処理量や調整待ちを無制限に増やさず運用できる性質とする。

- 登録や変更を処理する中央主体の作業量と待ち時間。
- 一覧のサイズ、配布回数、各取得者が必要とする帯域と処理量。
- 各組織が自らの範囲を変更できる度合いと、全体で一意性を保つための調整量。
- 分割後に必要となる委譲、参照、障害調査の複雑さ。

データ量の増加と、更新主体の増加を最後まで混同しない。前者は帯域と処理の問題であり、後者は権限と組織間調整の問題である。この章の主眼は後者にある。

## 3. 第一段――集中管理は何を解決したのか

**この節は短く書く。1段落から2段落。** 出来事の順序は第1章の担当であり、ここで年表を再語りしない。

RFC 606（1973年12月）は、集中した機械可読の表がまだ無い時点の状況を一人称で記録している。公式のホスト名一覧は存在したが機械可読の形でネットワーク越しに取得できず、各サイトが自前の表を手で維持していた。著者が挙げる4つのサイトはいずれも内容が異なり、どれも完全ではなかった。

> each site on the network must maintain a different, generally out-of-date, host list

引用は最小限にとどめ、「集中管理はより悪い分散状態への対処として始まった」という一点だけを確立して次へ進む。ここを厚くすると、拡張性の分析に入る前の前置きが長くなる。

RFC 608（1974年1月）でNICが実装を引き受け、更新は週次のバッチ生成として想定された。

## 4. 第二段――集中管理の仕組みと、それが詰まった理由

### 工程を分けて見る

一つのホスト表へホスト名とアドレスを登録し、各ホストが取得して利用する。この流れを、**登録、マスターの維持、配布、ローカルでの参照**という別々の工程として図示する。工程を分けないと、後の議論で「どの集中が問題だったのか」が曖昧になる。

集中管理、集中保管、集中配布を区別し、どれがどの問題を生んだかを対応づける。

### 登録の工程

RFC 810（1982年）のASSUMPTIONS第7項は、名前とアドレスをNICと**交渉して登録**することを、使用開始前の条件として定めている。連絡手段として電子メールアドレスと並んで電話番号が書かれている。自動化された手続きではなく、人を介した調整だった。

第6項は、取得した表を自分の用途の形式へ変換するのは利用者の責任だと定めている。

**負荷の定量的な記述は一次資料にない。** 工程がどういうものだったかは書けるが、それがどれほど重かったかを数値で語ることはできない。

### 更新主体の増加

データが同じ大きさでも、独立した組織からの登録・変更要求が増えると、検証、名前の調整、受付順序、責任確認が中央へ集中する。ここが帯域の問題と別であることを示す。

RFC 882（1983年11月）は、問題を規模の言葉で述べている。

> The size of this table, and especially the frequency of updates to the table are near the limit of manageability.

**表のサイズと、更新の頻度を並べつつ「especially」で後者に重心を置いている。** 同時代の文書が、量よりも更新の側に問題を見ていたことの裏付けになる。

### 配布の負荷について書けること、書けないこと

表全体の取得と、変更件数・取得主体の増加の関係を扱う。更新から各利用者の取得までに時間差があるため、同時点でも参照内容が異なり得ることを示す。

数値は書かない。ホスト数、ファイルサイズ、転送量の具体値は、RFC 606/608/810/952/882/921 のいずれにも存在しない。

RFC 1034（1987年）2.1節の「新版の配布に要する総帯域はホスト数の二乗に比例する」は紹介してよいが、**設計上の見積りとして扱う。** この記述はRFC 882（1983年）には無く、1987年の回顧で加わった定式化である。実測値として引用しない。

### 名前の一意性

平坦な名前空間では、一意性を中央が調整する。組織が独立に名前を選びたい要求と、ネットワーク全体で衝突を避ける要求が緊張する。

RFC 952（1985年）の命名規則は、調整を規則で代替する試みとして読める。先頭は英字、単一文字の名前は不可、ゲートウェイは名前に `-GATEWAY` または `-GW` を含めること。**平坦な名前空間では、役割や所属を名前の中に押し込む圧力がかかる。** これはRFC 882の設計目標と対照させると効く。

> names should not contain addresses, routes, or similar information as part of the name

**衝突の実例や発生頻度は書けない。** 中央が一意性を調整していた事実は一次資料から書けるが、具体的な衝突事例を示す記述はない。

### 可用性と単一障害点

マスターの保守・配布サービスが利用できない場合、新規取得や更新がどう影響を受けるかを扱う。取得済みのローカルコピーによって既知の名前は引ける点を併記する。「中央停止で全ての名前解決が即時停止した」とは書かない。

管理上の単一障害点と、問い合わせ時の単一障害点を区別する。

## 5. 問題を要件へ読み替える

| 問題 | 要件としての読み替え | 対応する設計 |
| --- | --- | --- |
| 中央への登録・調整集中 | 拡張性、運用性、管理の自律性 | 階層的名前空間、委譲、ゾーン |
| 一覧全体の反復配布 | 配布効率、性能 | 分散した権威情報、問い合わせ、キャッシュ |
| 変更の反映遅延 | 鮮度と負荷の制御 | TTL、ゾーン転送 |
| 平坦な名前の衝突 | 一意性と分散管理の両立 | 階層名と委譲 |
| 中央機能への依存 | 可用性、障害耐性 | 複数の権威サーバー、複製 |
| 既存利用からの移行 | 後方互換性、段階的移行 | 旧名に `.ARPA` を付ける互換措置、DHOSTS.TXTによる二重提供（RFC 921） |

この表は本書による分析枠組みであり、当時の文書が同じ非機能要件名を列挙したという主張ではない。

## 6. 第三段――階層化、ゾーン、委譲

- 階層的な名前空間によって、名前の一意性を部分木ごとの責任へ分解する考え方を説明する。
- ドメインを名前空間上の部分木、ゾーンを一つの管理主体が権威を持つ範囲として区別する。両者が一致するとは限らない理由を扱う。
- 委譲によって、親が全データを管理せず、子の管理主体と到達方法を示す設計を扱う。
- 分散した権威情報をリゾルバがたどることで、一括配布から必要な情報を問い合わせる方式へ責任を移す。
- 説明はRFC 1034/1035と現行用語（RFC 9499）を照合し、初期仕様と現在の用語差を明記する。

一意性の担保が実際に移し替えられたことは、同時代の方針文書が明記している。RFC 921（1984年10月）。

> The names are being changed from simple names, or globally unique strings, to structured names, where each component name is unique only with respect to the superior component name.

**この節の主張は本書の後付けの解釈ではない。** 当時の方針文書がそのまま述べている。

## 7. 効果、制約、他要件との衝突

### 得られる効果

- 登録・更新作業とデータ保持を管理範囲ごとに分け、中央が個々の変更を処理する必要を減らす。
- 組織が委譲された範囲を自律的に管理しながら、階層全体で名前を参照できる。
- 問い合わせとキャッシュにより、利用者全員へ一覧全体を繰り返し配る必要を減らす。

### 新しく生じる制約

- 親子の委譲情報、ゾーン境界、権威サーバーへの到達性という新しい設定と依存関係が生じる。
- 名前空間の階層と組織・運用上の境界が常に一致するとは限らず、ドメインとゾーンを区別する必要がある。
- 問い合わせ経路が多段になり、障害箇所と責任主体の切り分けが複雑になる。

### 他の非機能要件との衝突

- 分散は拡張性と自律性を助ける一方、整合性確認と運用の観測点を増やす。
- 委譲先の障害や誤設定は、その範囲の可用性へ影響する。分散だけで障害耐性が保証されるわけではない。
- キャッシュは配布負荷を減らす一方、変更反映を遅らせる。詳細は第3章と第5章が扱う。

### 移行はどう行われたか

新しい設計を決めることと、既に動いているものを移すことは別である。RFC 921 が示す移行の第一段は、**旧名に `.ARPA` を付けたものを新しい名前とする**という制約だった。名前空間を作り直すのではなく、既存の名前を新しい構造の中へ機械的に写し込んでいる。

表そのものも二重化された。新形式を別名のファイル（DHOSTS.TXT）で並行提供し、期日に本名（HOSTS.TXT）と入れ替え、旧版は OHOSTS.TXT として残す。

同文書は、前身のRFC 881が定めた予定が守られなかったことも記録している。この点は第9章（後方互換性と発展性）で扱う。ここでは移行措置の存在までを示す。

## 8. 運用上の注意と他システムへの応用

- 管理責任を分ける際は、データの分割だけでなく、権限、参照方法、障害時の連絡先、境界をまたぐ整合確認を設計する。
- 階層化が適するのは、全体の一意性を保ちながら部分ごとに安定した責任主体を置ける場合である。変更が常に複数境界をまたぐシステムでは調整コストが残る。
- 分割後の局所最適だけでなく、参照経路の長さ、共通依存先、誤設定の影響範囲を評価する。
- **集中を選ぶ条件も併記する。** 第一段が示すように、主体が少なく調整が軽いうちは集中した一覧のほうが正しさを保ちやすい。分散が常に優れているわけではない。

## 11. 本文で断定を避けるべき点

- DNSが「一人」または「一つの問題」だけによって発明されたという単純化。
- HOSTS.TXTの中央機能が停止すると、取得済み情報を含む全名前解決が直ちに止まったという表現。
- ホスト数、ファイルサイズ、転送回数、衝突件数の、出典と時点を欠く数値。
- RFC 1034の二乗則を、当時の実測値または当時の文書の主張として扱うこと。
- 階層化、委譲、キャッシュのどれか一つが、すべての拡張性問題を解決したという評価。
- 後世の用語や現在の役割分担が、移行期にも同じだったという前提。
- RFC 1034の回顧だけを、1980年代初頭の全運用実態を直接観測した記録として扱うこと。
- **集中管理を、当時の条件を無視して誤った選択として扱うこと。** 第一段が示すように、集中はより悪い分散状態への対処だった。
